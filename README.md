# lab02_ab-320_sychuk

Лабораторная работа №2: классификация подозрительных событий аутентификации.

**Вариант 3 (№21 в списке).** Фокусные поля: `timestamp`, `hour`, `is_weekend`, `device_type`, `os_family`, `browser_family`, `known_device`. Основная проверка - временное разделение по `timestamp`.

## Задача

Построить учебный классификатор подозрительных попыток входа, сравнить несколько методов на одном протоколе и выбрать модель с порогом при ограниченной емкости ручной проверки. Целевая переменная `is_suspicious`: `0` - нормальное событие, `1` - подозрительное. Результат предназначен для аналитика SOC: приоритизация проверок при ограниченном лимите алертов.

## Выполненные этапы

1. **Подготовка данных.** Загрузка листа `data`, сохранение `source_row_id`, очистка по правилам ЛР №1 и удаление полных дубликатов. Медианное заполнение числовых пропусков и ограничение `password_age_days` выполняются внутри `Pipeline`: медианы оцениваются только на train. Исходно 1430 строк, после очистки и дедупликации - 1299 строк, 16 признаков в `X`.
2. **Разделение.** Внешний test - последние 20 % строк по `timestamp`, как в ЛР №1; из оставшихся строк последние 25 % по времени выделены в validation. Хронология строгая: train < validation < test.
3. **Обучение.** `DummyClassifier(strategy="most_frequent")` как baseline, затем `LogisticRegression`, `RandomForestClassifier` и `KNeighborsClassifier` - по одной исходной настройке и одному заранее обоснованному изменению. Каждый опыт получает новый экземпляр конвейера через `clone()`, `fit` выполняется только на train.
4. **Выбор порога.** Для каждой конфигурации перебираются уникальные score на validation и `threshold = np.inf`. Лимит - 120 алертов на 1000 событий, для validation это 31 алерт. Выбор: максимальный recall, затем precision, меньше алертов, больший threshold; между моделями - recall, precision, меньше алертов, AP.
5. **Проверка на test.** Выбранная модель и порог зафиксированы до test, переобучения на train+validation нет. Разобраны FP/FN и подгруппы фокусных признаков.

## Результаты

**Разделение:**

| Часть | Строк | Класс 1 | Доля класса 1 |
|---|---:|---:|---:|
| train | 780 | 55 | 7.05 % |
| validation | 259 | 13 | 5.02 % |
| test | 260 | 42 | 16.15 % |

**Выбранная модель:** `RandomForestClassifier(n_estimators=200, max_features="sqrt", min_samples_leaf=1, random_state=42, n_jobs=-1)`, порог `0.1550`.

| Часть | Recall | Precision | F1 | AP | Алертов | Cost = FP + 20*FN |
|---|---:|---:|---:|---:|---:|---:|
| validation | 0.9231 | 0.4286 | 0.5854 | 0.8086 | 28 из 259 (108.1 / 1000) | 36 |
| test | 0.5000 | 0.8077 | 0.6176 | 0.7114 | 26 из 260 (100.0 / 1000) | 425 |

Baseline `DummyClassifier` на validation имеет recall 0 и AP 0.0502. Альтернативный порог `0.1085` на validation даёт recall 1.0 и cost 23, но поднимает 36 алертов при лимите 31, поэтому не используется.

## Ограничения

1. Набор синтетический, правило разметки и генерации признаков неизвестно.
2. Проверен только один будущий временной период; доля класса 1 в test заметно выше, чем в train и validation.
3. Порог `0.1550` выбран на validation и переносится на test без изменений; при временном дрейфе требуется мониторинг доли алертов и периодический пересмотр порога.
4. Выбранная модель имеет низкую precision на validation (0.4286, 16 FP из 28 алертов); подгрупповые оценки нестабильны из-за малого числа положительных объектов.
