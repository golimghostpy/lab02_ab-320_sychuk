## Выполненные этапы

1. **Подготовка данных.** Загрузка листа `data`, сохранение `source_row_id`, очистка по правилам ЛР №1 и удаление полных дубликатов. Медианное заполнение числовых пропусков и ограничение `password_age_days` значением `account_age_days` выполняются внутри `Pipeline` (медианы оцениваются только на train). Исходно 1430 строк, после очистки и дедупликации — 1299 строк, 16 признаков в `X`.
2. **Разделение.** Внешний test — последние 20 % строк по `timestamp`, как в ЛР №1; из оставшихся строк последние 25 % по времени выделены в validation. Хронология строгая: `max(train) < min(validation) < min(test)`.
3. **Обучение.** `DummyClassifier(strategy="most_frequent")` как baseline, затем `LogisticRegression`, `RandomForestClassifier` и `KNeighborsClassifier` — по одной исходной настройке и одному заранее обоснованному изменению. Каждый опыт получает новый экземпляр конвейера через `clone()`, `fit` вызывается только на train.
4. **Выбор порога.** Для каждой конфигурации перебираются уникальные score на validation и `threshold = np.inf`. Лимит — 120 алертов на 1000 событий, для validation это 31 алерт. Внутри конфигурации: максимальный recall → precision → меньше алертов → больший threshold. Между моделями: recall → precision → меньше алертов → AP.
5. **Проверка на test.** Выбранная модель и порог зафиксированы до test, переобучения на train+validation нет. Разобраны FP/FN и подгруппы фокусных признаков.

## Почему не RandomForest `min_samples_leaf=1`

На validation RF `min_samples_leaf=1` формально показывает лучший recall (0.9231 против 0.8462 у LR), но исключён как переобученный: AP на train = 1.0000, на validation = 0.8086, разрыв 0.1914. Модель запомнила тренировочные события, а не общие закономерности, поэтому её вероятности на новых данных хуже упорядочены. После исключения этой конфигурации по правилу (recall → precision → меньше алертов → AP) выбрана `LogisticRegression(C=1)`.

## Дополнительный разбор `known_device`

По ноутбуку на test 18 из 25 FN приходятся на подгруппу `known_device = 1`. Доля класса 1 внутри неё выросла с 7/236 = 3.0 % на validation до 26/234 = 11.1 % на test — фиксированный порог не успевает за этим сдвигом.

| Часть | `known_device` | Всего | Класс 1 | TP | FP | FN | Recall |
|---|---:|---:|---:|---:|---:|---:|---:|
| validation | 0 | 23 | 6 | 4 | 4 | 2 | 0.667 |
| validation | 1 | 236 | 7 | 7 | 2 | 0 | 1.000 |
| test | 0 | 26 | 16 | 9 | 1 | 7 | 0.562 |
| test | 1 | 234 | 26 | 8 | 2 | 18 | 0.308 |

На validation лучше ловятся известные устройства, на test — неизвестные: направление ошибки меняется, что говорит о сдвиге распределения, а не о переносе сигнала `known_device`. Абсолютные значения recall нестабильны из-за малого числа положительных на validation.

## Ограничения

1. **Синтетическая природа данных.** Правило разметки и генерации признаков неизвестно, возможны скрытые зависимости между полями.
2. **Сценарий разделения.** Проверен только один будущий временной период; доля класса 1 в test (16.15 %) заметно выше, чем в train и validation. Пользователи `user_id` пересекаются между частями — модель проверена на будущих событиях уже известных пользователей, но не на полностью новых учётных записях.
3. **Перенос порога.** Порог `0.3026` выбран на validation и применён к test без изменений. Из-за временного дрейфа распределения recall упал с 0.8462 до 0.4048 (на ~44 п.п.), а precision выросла до 0.8500. В эксплуатации требуется мониторинг доли алертов и периодический пересмотр порога.
4. **Подгрупповые оценки нестабильны.** На validation всего 13 положительных объектов, на test — 42; оценки по `known_device` опираются на единицы наблюдений и не годятся как точечные характеристики качества.
