## Блок 1: Подготовка данных

### Что делаем
- Загружаем датасет из lab01
- Очищаем данные по предметным правилам
- Заполняем пропуски медианой (для числовых) и категорией Other (для категориальных)
- Удаляем дубликаты
- Формируем матрицу признаков X и целевую переменную y

### Зачем это нужно в ML
**Очистка данных** — критический этап. Мусор на входе = мусор на выходе. Ошибки в данных (отрицательный возраст, невалидные ID) могут полностью разрушить обучение модели.

**Заполнение пропусков**:
- Медиана устойчива к выбросам (в отличие от среднего)
- Категория Other сохраняет строки, не теряя информацию о наличии пропуска

**Дедупликация** — предотвращает "запоминание" моделью конкретных объектов. Если дубликаты попадут и в train, и в test — метрики будут завышены.

**source_row_id** — уникальный идентификатор строки. Нужен для воспроизведения разбиения из lab01. Без него невозможно гарантировать, что test будет тем же самым.

## Блок 2: Разделение выборки (train / validation / test)

### Что делаем
- Воспроизводим test из lab01 по event_id
- Из оставшихся данных (train+validation) выделяем validation — последние 25% по времени
- Проверяем хронологию: train < validation < test

### Зачем это нужно в ML

**Три выборки вместо двух:**
- **train** — для обучения модели (fit)
- **validation** — для выбора модели и гиперпараметров
- **test** — для финальной оценки (используется один раз в конце)

**Почему нельзя обойтись без validation?**
Если выбирать модель по test, происходит "подгонка под test" — модель не будет работать на новых данных. Test должен быть "святым" — не использоваться ни в каких решениях до финальной оценки.

**Временное разделение (вариант 3):**
- Соответствует реальному сценарию: обучение на прошлом, применение к будущему
- Проверяет устойчивость модели к временному дрейфу
- Хронология обязательна: если событие из test попадёт в train — это утечка данных

**Проверка пересечений по пользователям:**
- Если пользователь есть и в train, и в test — модель может "узнать" его по стилю поведения
- Это не прямая утечка (user_id исключён из признаков), но может завышать метрики

## Блок 3: Preprocessing Pipeline

### Что делаем
- Создаём ColumnTransformer для обработки числовых и категориальных признаков
- Числовые: SimpleImputer(median) + RobustScaler
- Категориальные: SimpleImputer(most_frequent) + OneHotEncoder(handle_unknown='ignore')

### Зачем это нужно в ML

**Pipeline вместо ручной обработки:**
- Гарантирует, что fit вызывается только на train
- Предотвращает утечку статистик test в train
- Воспроизводимость: один и тот же pipeline можно сохранить и загрузить

**RobustScaler вместо StandardScaler:**
- В данных есть выбросы (distance=20000, attempts=999)
- StandardScaler (среднее + стд) чувствителен к выбросам
- RobustScaler (медиана + IQR) устойчив — выбросы не влияют на масштаб

**OneHotEncoder(handle_unknown='ignore'):**
- В test могут появиться новые категории (новая страна, новое устройство)
- Без handle_unknown='ignore' pipeline упадет
- С этой опцией неизвестные категории игнорируются (все нули)

**Важно:** fit только на train! Если случайно вызвать fit на всём датасете — информация из test утечёт в параметры скейлера и энкодера.

## Блок 4: Обучение моделей (Baseline + 3 классификатора × 2 конфигурации)

### Что делаем
- DummyClassifier(strategy='most_frequent') — baseline
- LogisticRegression (C=1 и C=0.1)
- RandomForest (min_samples_leaf=1 и 5)
- KNeighbors (n_neighbors=5 и 15)

### Зачем это нужно в ML

**Baseline (DummyClassifier):**
- Показывает, какой результат можно получить без обучения
- Если модель не побивает baseline — она бесполезна
- Для дисбаланса классов baseline="most_frequent" даёт high accuracy, но recall=0

**Изменение гиперпараметров:**

**LogisticRegression, C: 1 → 0.1**
- C — обратная сила регуляризации (меньше C = сильнее регуляризация)
- Регуляризация предотвращает переобучение
- Меньше C = более простая модель = меньше шанс переобучиться

**RandomForest, min_samples_leaf: 1 → 5**
- min_samples_leaf ограничивает глубину дерева
- 1 = листья из одного объекта = сильное переобучение
- 5 = минимум 5 объектов в листе = более общие правила

**KNeighbors, n_neighbors: 5 → 15**
- Меньше соседей = более сложная модель = выше риск переобучения
- Больше соседей = более устойчивые предсказания = сглаживание

**Почему именно эти изменения?**
Изменения выбраны до просмотра результатов — это важно. Если подбирать гиперпараметры по результатам, происходит "подгонка под validation".

## Блок 5: Выбор порога по лимиту алертов

### Что делаем
- Лимит: 120 алертов на 1000 событий
- Для каждой модели перебираем уникальные пороги на validation
- Среди допустимых (алертов ≤ лимит) выбираем лучшую по правилу:
  1. Максимальный recall
  2. Максимальный precision
  3. Минимальное число алертов
  4. Максимальный threshold
  5. Максимальный AP

### Зачем это нужно в ML

**Почему нельзя использовать predict()?**
- predict() использует порог 0.5 по умолчанию
- Для дисбаланса классов (8.5% класса 1) порог 0.5 может быть неоптимален
- Выбор порога — это управление компромиссом precision/recall

**Бизнес-ограничение (лимит алертов):**
- В реальном SOC аналитик не может проверить 1000 алертов в день
- Лимит — это ресурсное ограничение
- Порог подбирается так, чтобы не превысить лимит

**Правило выбора:**
1. **Recall** — главная метрика: найти как можно больше угроз
2. **Precision** — вторичная: среди найденных угроз как можно больше реальных
3. **Алерты** — минимизируем, чтобы не перегружать аналитика
4. **Threshold** — больший порог = строже фильтр = меньше шансов на случайные срабатывания
5. **AP** — при полном равенстве берём модель с лучшим качеством score

**Порог np.inf (без алертов):**
- Всегда рассматриваем вариант "не поднимать алерты вообще"
- Если recall=0 — значит, лимит слишком жёсткий

## Блок 6: Проверка на test

### Что делаем
- Применяем выбранную модель с фиксированным порогом к test
- Вычисляем метрики
- Сохраняем detector.joblib

### Зачем это нужно в ML

**Критически важно: модель НЕ переобучается на train+validation!**
- После выбора модели по validation мы НЕ объединяем train+validation
- Модель остаётся обученной только на train
- Это гарантирует честную оценку на test

**Порог фиксирован:**
- Порог выбран по validation
- На test применяем тот же порог без изменений
- Если подгонять порог под test — оценка будет смещена

**Метрики на test могут отличаться от validation:**
- Это нормально — test из другого временного периода
- Доля класса 1 на test (15.77%) выше, чем на train (6.76%) — временной дрейф
- Лимит алертов на test может не выполняться — это наблюдаемый результат

**Сохранение модели:**
- detector.joblib содержит pipeline + threshold
- Можно загрузить и применить к новым данным

## Блок 7: Анализ ошибок

### Что делаем
- Показываем примеры FP (ложные срабатывания)
- Показываем примеры FN (пропущенные угрозы)
- Анализируем по фокусным признакам

### Зачем это нужно в ML

**FP (False Positive):**
- Модель сказала "подозрительно", но это нормальное событие
- Стоимость: время аналитика на проверку
- Если FP много — аналитик перестаёт доверять системе

**FN (False Negative):**
- Модель сказала "нормально", но это угроза
- Стоимость: пропущенная атака
- В ИБ это критическая ошибка — одна пропущенная атака может стоить дороже 100 ложных тревог

**Анализ по признакам:**
- Позволяет понять, почему модель ошибается
- Может указать на недостатки признаков или данных
- Помогает принять решение о доработке модели

**Recall по подгруппам:**
- Позволяет выявить систематические ошибки
- Например: модель плохо работает на мобильных устройствах
- Основа для улучшения модели (добавить признаки, изменить архитектуру)

## Блок 8: PR-кривая

### Что делаем
- Строим Precision-Recall кривую на validation
- Отмечаем рабочую точку (выбранный порог)

### Зачем это нужно в ML

**Почему PR-кривая, а не ROC?**
- ROC оптимистичен при дисбалансе классов
- PR-кривая показывает реальную картину для редкого класса
- AP (Area under PR curve) — метрика качества score

**Рабочая точка:**
- Показывает, где на кривой находится выбранный порог
- Визуализация компромисса precision/recall
- Позволяет оценить, сколько "запаса" есть по recall

**Сравнение FP/FN:**
- Барчарт показывает баланс ошибок для разных моделей
- Помогает понять, какая модель лучше подходит под задачу
- В ИБ обычно важнее минимизировать FN

## Ключевые принципы, соблюдённые в работе

### 1. Предотвращение утечки данных
- fit() только на train
- transform() на validation и test
- Test не используется при выборе модели и порога

### 2. Правильный порядок разделения
- Сначала исключаем test (из lab01)
- Затем выделяем validation из train (не из всей таблицы)
- Хронология: train < validation < test

### 3. Фиксация решений
- Модель выбрана по validation
- Порог выбран по validation
- На test — только оценка, никаких изменений

### 4. Учёт бизнес-ограничений
- Лимит алертов учитывается при выборе порога
- Компромисс FP/FN явно обозначен
- Стоимость ошибок описана

## Что НЕ сделано (и почему это правильно)

### НЕ переобучаем на train+validation
- Это была бы ошибка: утечка validation в модель
- После выбора модели по validation её нельзя использовать для обучения

### НЕ подгоняем порог под test
- Порог выбран по validation и зафиксирован
- На test — только наблюдение результата

### НЕ используем GridSearchCV
- По заданию: один исходный опыт + одно изменение гиперпараметра
- GridSearchCV подбирает по validation, но скрывает процесс

### НЕ используем ROC-AUC
- По заданию: AP (Average Precision)
- Для дисбаланса классов AP информативнее ROC-AUC
